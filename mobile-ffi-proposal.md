# Mobile / FFI port proposal — userver-free SlugKit generator

**Status:** draft / exploration
**Goal:** ship the SlugKit generator engine to mobile (iOS/Android) and other
runtimes as a native library consumable from Swift, Kotlin/Java, and Dart via a
stable C ABI. Prerequisite: build the engine *without* the `userver` dependency.

---

## 1. Why this is feasible

The generator is almost pure algorithmic C++. It does **no I/O, no networking,
no coroutines** in its hot path. The `userver` coupling is shallow and falls
into a handful of well-understood categories, every one of which has a small
standalone replacement. There is no async/coroutine logic to unwind — the one
coroutine primitive in use (`engine::SharedMutex`) guards a process-wide locale
cache and can be a plain `std::shared_mutex`.

## 2. Current coupling inventory

Audited across `slugkit/include` and `slugkit/src`.

### 2.1 userver utility types (trivial to shim)

| userver API | Used in | Replacement |
|---|---|---|
| `utils::StrongTypedef` / `IsStrongTypedef` (5) | `types.hpp`, `text.hpp`, `numeric.hpp`, `binary/dictionary_detail.hpp`, `structured_loader.hpp` | ~80-line header-only strong typedef |
| `utils::FastPimpl` (4) | `generator.hpp`, `dictionary.hpp`, `memory_mapped_file.hpp`, `pattern_generator.hpp` | well-known ~50-line `fast_pimpl` |
| `cache::NWayLRU` (2) | `binary_dictionary.hpp`, `detail/caches.hpp` | small sharded LRU |
| `utils::TrivialBiMap` (1) | `io/types_io.hpp` | constexpr `std::array` lookup |
| `UASSERT` (1) | `permutations.cpp` | `assert` / custom macro |
| `logging::LogHelper` (1) | `io/userver_logging.hpp` | no-op or pluggable log callback |
| `engine::SharedMutex` (1) | `utils/text.cpp` | **toggled** via compat (see ⚠ below) |

None of these affect behaviour or output; they are vocabulary types and helpers.

> ⚠ **`std::shared_mutex` cannot be used in userver code** (it blocks the OS
> thread instead of yielding the coroutine). So the mutex must go through the
> compat seam, *not* be hardcoded: `SLUGKIT_USE_USERVER=ON` keeps
> `userver::engine::SharedMutex`; `OFF` uses `std::shared_mutex`. Add
> `compat::SharedMutex` as the alias point.

### 2.2 Third-party libs currently provided *via* userver

| Dependency | Used for | Mobile decision |
|---|---|---|
| `fmt` (bundled by userver) | formatting / error messages, widely used | depend on **standalone fmtlib** (trivial cross-compile) |
| `userver::formats::yaml/json` | (a) `structured_loader` dictionary loading, (b) **emoji dict loaded at runtime from embedded YAML** (`pattern_generator.cpp:72`) | see §4.2 — eliminate runtime YAML on mobile |
| `boost` headers: `functional/hash`, `range`, `algorithm/string`, `multiprecision/cpp_int` | hashing, capacity bignum, string ops | **header-only**, keep (no compiled boost needed) |
| **`boost::locale` (+ ICU)** | locale-aware `ToLower`/`ToUpper`/title-case in `utils/text.cpp` | see §4.1 — **the one heavy dependency**; replace with `utf8proc` |

### 2.3 Build-system coupling

- `userver_embed_file()` (CMake) embeds `data/emoji.yaml` and test data into the
  binary (`#include <generated/emoji.yaml.hpp>`). Needs a portable embed step
  (CMake-generated byte array) — or is removed entirely if emoji is precompiled
  (§4.2).

### 2.4 Platform surface

- `utils/memory_mapped_file.cpp` uses POSIX `mmap` — works on iOS/Android, but
  file access is sandboxed. The binary `DictionarySet` should also be
  constructible from an in-memory buffer (asset bytes), not only a file path.

## 3. Target architecture

```
                +-----------------------------------+
                |   slugkit-generator (core C++)    |
                |   no userver, no ICU              |
                +-----------------------------------+
                |  slugkit/compat/  (shim layer)    |  <- swapped by CMake flag
                |  strong_typedef / fast_pimpl /    |
                |  lru / assert / log / mutex       |
                +-----------------------------------+
                            |
                +-----------------------------------+
                |  slugkit_c  (extern "C" ABI)      |  <- the FFI substrate
                +-----------------------------------+
                  |            |            |
              Swift pkg    Kotlin/JNI    Dart ffi      (+ optional WASM)
             (XCFramework) (.so + AAR)  (Flutter pkg)
```

### 3.1 Compat layer, toggled — not forked

Add `slugkit/include/slugkit/compat/` with the standalone implementations and a
single switch:

- `SLUGKIT_USE_USERVER=ON` (default) → `compat` headers alias to userver types,
  so the existing `gen` service build is **byte-for-byte unchanged**.
- `SLUGKIT_USE_USERVER=OFF` → `compat` headers provide standalone impls.

This keeps one source tree serving both the service and the mobile target;
no parallel fork to maintain. The migration is mechanical: replace
`userver::utils::StrongTypedef` etc. in core code with `slugkit::compat::...`.

### 3.2 C ABI (`slugkit_c`)

Opaque-handle C API — the universal FFI substrate (Swift imports C directly,
Dart `dart:ffi` binds C directly, Kotlin via JNI/cinterop):

```c
slk_generator* slk_generator_create_from_binary_buffer(const uint8_t* data, size_t len, char** err);
void           slk_generator_destroy(slk_generator*);
int            slk_capacity(slk_generator*, const char* pattern, slk_capacity_out*, char** err);
int            slk_generate(slk_generator*, const char* pattern, const char* seed,
                            uint64_t seq, char* out, size_t out_cap, char** err);
int            slk_generate_batch(slk_generator*, const char* pattern, const char* seed,
                                  uint64_t seq, size_t count, slk_emit_cb, void* ctx, char** err);
void           slk_string_free(char*);
```

Rules: no C++ types across the boundary; errors as return code + out-param
message; caller-or-callee-frees contract documented; UTF-8 throughout. Wrap the
existing `Generator` (`generator.hpp`) — the API is already callback-based for
batches, which maps cleanly.

### 3.3 Per-language bindings

- **iOS/macOS (Swift):** static lib + module map packaged as an **XCFramework**
  (device arm64, simulator arm64/x86_64, macOS). Thin Swift wrapper over the C
  API. Distribute as a SwiftPM binary target.
- **Android (Kotlin):** build `.so` for `arm64-v8a`, `armeabi-v7a`, `x86_64` via
  NDK; JNI shim + Kotlin wrapper; package as an AAR.
- **Flutter/Dart:** `dart:ffi` directly against `slugkit_c.h`; ship as a Flutter
  plugin bundling the per-platform binaries (reuses the iOS/Android artefacts).
- **(Optional) WASM/web:** Emscripten target for parity with the web SDK.

## 4. Key dependency decisions

### 4.1 Drop `boost::locale` / ICU → `utf8proc`

This is the single most important call. `boost::locale` pulls in **ICU**, which
is heavy and awkward to cross-compile for iOS (Android has system ICU but it is
not a stable NDK API). It is used *only* for case conversion in `utils/text.cpp`.

Replace with **utf8proc** (single-file, ~liberal licence, full Unicode case
mapping, trivial to cross-compile). Consequence: **the remaining boost usage is
header-only**, so mobile builds need *no compiled third-party except fmt and
utf8proc*. This replacement can be done **library-wide** (not just the mobile
build) — confirmed acceptable. Turkish characters have only just landed in
SlugKit, so the locale-tailored `i` edge case is low-stakes; the golden suite
(§6, Phase 0) must still include Turkish casing so the utf8proc output is
captured as the new reference.

### 4.2 Eliminate runtime YAML on mobile → precompile emoji to binary

Today even the binary-dictionary path parses YAML at startup to load the emoji
dictionary (`pattern_generator.cpp:72`). For mobile:

> **Out of scope here:** the emoji dictionary is being carved out of the YAML
> runtime path by separate work (another worktree). This proposal defers the
> emoji mechanics to that effort and only assumes its outcome: no runtime YAML
> needed for emoji.

- Use the existing binary-dictionary tooling (`slugkit/py/tools/.../compile_dict.py`,
  `examples/bin-dict`) to **precompile `emoji.yaml` into the binary dict format**
  at build time, embedded as a byte array.
- The mobile build then has **zero runtime YAML/JSON** and excludes
  `structured_loader` + `io/*` entirely (gated behind
  `SLUGKIT_GENERATOR_WITH_SERIALIZATION`).
- Desktop/service builds keep YAML loading (standalone **yaml-cpp** when
  userver-free, or userver formats when not).

### 4.3 fmt

Depend on standalone **fmtlib** via FetchContent/submodule when userver-free.
Header/compiled, cross-compiles cleanly to all targets.

### 4.4 boost (header-only) and bignum

Keep `boost::multiprecision::cpp_int` for capacity maths (header-only). If we
later want to drop the boost include dependency too, `cpp_int` is replaceable
with a small fixed-width bignum or `__int128` where range allows — out of scope
for v1.

## 5. Toolchains

Add `cmake/toolchains/`:

- `android-ndk.cmake` (wraps `$NDK/build/cmake/android.toolchain.cmake`; ABIs + API level).
- `ios.cmake`, `ios-simulator.cmake` (device arm64 / sim arm64+x86_64; e.g. based on `leetal/ios-cmake`).
- `macos-arm64.cmake` (host bindings + tests).
- `wasm-emscripten.cmake` (optional).

Plus a presets file (`CMakePresets.json`) per target and a `Makefile`/CI matrix
that produces the XCFramework, AAR, and Flutter plugin artefacts.

## 6. Phased plan

**Phase 0 — de-risk (1–2 days).** Spike: compile the core (no FFI) for host with
`SLUGKIT_USE_USERVER=OFF`, stubbing only what's needed, to surface hidden
coupling. Diff slug output vs the userver build on a fixed seed corpus —
establishes the **golden regression suite** used everywhere below.

**Phase 1 — compat layer.** Implement `slugkit/compat/*` (strong_typedef,
fast_pimpl, lru, assert, log, mutex) + the `SLUGKIT_USE_USERVER` switch. Migrate
core code off direct userver includes. Service build stays green; tests pass.

**Phase 2 — dependency swap.** `boost::locale`→`utf8proc`; `fmt` standalone;
gate serialization behind `SLUGKIT_GENERATOR_WITH_SERIALIZATION`; precompile
emoji to binary + portable embed. Core now builds userver-free on host. Golden
suite must match.

**Phase 3 — C ABI.** Implement `slugkit_c` + header; add buffer-based binary
dict construction; unit-test the C API on host.

**Phase 4 — toolchains + first mobile artefact.** Android `.so` and iOS
XCFramework building in CI; run the golden suite on-device/emulator.

**Phase 5 — language bindings.** Swift package, Kotlin/AAR, Flutter/Dart plugin,
each with a smoke test calling generate/capacity.

**Phase 6 — packaging & docs.** Versioned artefacts, integration examples,
size/perf report per platform.

## 7. Risks & open questions

- **Locale casing parity (utf8proc vs ICU):** must be validated by the golden
  suite. If language-tailored casing is required, fall back to bundling a
  trimmed ICU or platform casing APIs behind the compat seam.
- **Binary size:** measure per-arch; emoji + dictionary data dominate. Consider
  on-demand asset loading vs embedding.
- **Dictionary delivery on device:** prefer binary dict from app assets / buffer;
  confirm `binary::DictionarySet` can be built from a buffer without `mmap`.
- **`FastPimpl` fixed sizes:** the hardcoded `kImplSize`/`kImplAlign` in headers
  must stay correct across toolchains (assert at compile time; the standalone
  fast_pimpl already static_asserts).
- **Thread-safety expectations:** confirm `Generator` is safe for concurrent
  `Generate` calls once the locale cache uses `std::shared_mutex`.
- **Licensing:** confirm utf8proc / fmt / yaml-cpp licences are compatible for
  app store redistribution.

## 8. First concrete step

Phase 0 spike + golden regression corpus. Everything downstream is gated on
"does the userver-free build produce byte-identical slugs?" — stand that test up
first.

## Phase 0 results

Executed on macOS (Apple clang 17, libc++, C++20), Homebrew fmt/boost/utf8proc/googletest.
Self-contained host project at `slugkit/host/` builds the generator **core** with no userver.

### Build status

- **Core compiles userver-free: yes.** All 15 core sources build into
  `slugkit-generator-host` with no `SLUGKIT_USE_USERVER` and no
  `SLUGKIT_GENERATOR_WITH_SERIALIZATION` defined (compat shims use their standalone
  branches; numeric serialisation compiled out).
- **Golden test passes: yes — 9/9.** Byte-identical committed expectations reproduced
  (lower/upper/title case, decimal numbers, the full-slug `GenerateID` corpus,
  `GetCapacity`), plus the PR #20 property-based mixed-case assertions
  (`MixedCapacity()==80`, capacity 80, 80 collision-free cased forms each lowercasing
  to a base noun). The mixed-case + `ToLower` path exercises utf8proc.

Build / run:

```sh
cd libs/generator/trees/side-quests
cmake -S slugkit/host -B slugkit/host/build -DCMAKE_PREFIX_PATH=/opt/homebrew
cmake --build slugkit/host/build -j
./slugkit/host/build/golden_test
```

### Hidden coupling discovered (beyond the anticipated include/qualifier swaps)

- **`filter/filtered_ids.hpp`** (core, not under `io/`) `fmt::format`s `IndexType`
  strong typedefs directly. Under userver this worked via userver's StrongTypedef
  fmt formatter; the compat header documented that typedefs are "never fmt-formatted
  directly". Fixed by also adding an fmt formatter to the compat StrongTypedef (see below)
  and extracting `.GetUnderlying()` at this call site.
- **`detail/pattern_parser.hpp`** uses `fmt::format` but never `#include`d fmt — it
  relied on a transitive include from userver headers. Added `#include <fmt/format.h>`.
- **`generator/dictionary.cpp`** called `language.empty()` on a `LanguageCode`
  strong typedef (userver's StrongTypedef forwards container ops; the compat one does
  not). Fixed the call site to `language.GetUnderlying().empty()`.
- **`generator/dictionary.cpp` / `detail/indexes.cpp`** construct `Tag` / `LanguageCode`
  (underlying `std::string`) from a `std::string_view` (`Tag(view.GetUnderlying())`).
  The compat single-value ctor only took `const T&`/`T&&`; `string_view → string` is
  explicit so this failed. Added a constrained generic single-arg ctor to compat.
- **`utils/set.hpp`** (`IsSubset`/`Intersects`) compares `Tag` (underlying `std::string`)
  against `std::string_view` via `std::count`. The compat transparent comparisons only
  compared against the exact underlying `T`. Made the compat transparent comparisons
  templated over any RHS comparable with the underlying.
- **Many fmt sites** format `LanguageCodeView` / `TagView` / `IndexType` / `SizeType`
  typedefs directly (`binary_dictionary.cpp`, `binary/dictionary_detail.hpp`). Resolved
  centrally by the compat fmt formatter rather than touching each site.

### FastPimpl size deltas (clang/libc++, standalone compat vs the hardcoded header constants)

| Type | header `kImplSize`/`Align` | actual `sizeof`/`alignof` (clang/libc++) | verdict |
|---|---|---|---|
| `utils::MemoryMappedFile::Impl` | 24 / 8 | 24 / 8 | exact match |
| `generator::Dictionary::Impl` | 216 / 8 | 80 / 8 | header far over-provisioned |
| `generator::Generator::Impl` | 144 / 8 | 56 / 8 | header over-provisioned |
| `generator::PatternGenerator::Impl` | 160 / 16 | 144 / 16 | header over-provisioned |

The constants are **not portable as exact sizes** — they were tuned for the
userver/gcc+libstdc++ build, where the Impls are larger (userver `SharedMutex`,
`NWayLRU`, etc.). Under the standalone compat shims the Impls shrink substantially.

**Resolved:** each constant is now declared per-build in the header behind
`#ifdef SLUGKIT_USE_USERVER` / `#else`, with uniform names/declarations
(`static constexpr std::size_t kPimplSize`/`kPimplAlign`, `UL`-suffixed). The
standalone values were verified **exact** by temporarily tightening the compat
`FastPimpl` assert to `Size == sizeof(T)` and rebuilding (no assertion fired);
the assert was reverted to `Size >= sizeof(T)`, which is retained as a safety net
so future small growth degrades to oversize-but-safe rather than a hard break.
Alignments are stable (8/8/8/16). `MemoryMappedFile::Impl` is identical across
toolchains, so it keeps a single unguarded value.

### utf8proc vs boost::locale

`utils/text.cpp` case conversion (`ToLower`/`ToUpper`/`Capitalize`/`FirstUpper`)
reimplemented on utf8proc (decode → `utf8proc_tolower`/`toupper` → re-encode). The
`GetLocale`/`boost::locale::generator` cache and its userver `SharedMutex` were
removed (no longer needed). `MixedCase` keeps its byte-indexed mask model and applies
ASCII case rules to ASCII letters only, passing all other bytes (including multi-byte
UTF-8 sequence bytes) through unchanged — matching `CountCaseToggleable`/`ExpandCaseMask`.

- **ASCII: no differences** — all ASCII golden expectations pass byte-for-byte.
- **Turkish probe (reference capture, not ICU parity):** input `İSTANBUL gıda Ğit`
  → lower `istanbul gıda ğit`, upper `İSTANBUL GIDA ĞIT`. utf8proc applies the
  locale-independent Unicode default case mappings: `İ`→`i` (no Turkish dotless-i
  tailoring), `ı`→`I`, `Ğ`↔`ğ`. Stable across calls. Locale-tailored casing remains a
  TODO (marked in `text.cpp`); fall back to ICU/platform casing behind the compat seam
  if required.

### Compat-header changes made (all in the standalone `#else` branch only; userver branch untouched)

- `compat/strong_typedef.hpp`: added a constrained generic single-arg ctor
  (`T` constructible from `U`, e.g. `Tag{string_view}`); made the transparent
  comparison operators templated over any RHS comparable with the underlying type;
  added an `fmt::formatter` specialisation forwarding to the underlying type's
  formatter (`#include <fmt/format.h>` added to the standalone branch).
- `compat/lru_cache.hpp`: the `Shard` holds a `std::mutex` (not move-insertable), so
  `std::vector<Shard>::resize` was ill-formed under libc++; switched shards to
  `std::vector<std::unique_ptr<Shard>>` built in place (`#include <memory>`).

### Service CMake wiring — DONE (in `slugkit/CMakeLists.txt`, untested here: no userver in this env)

- `option(SLUGKIT_USE_USERVER ... ON)` added. When ON the two targets get the
  `SLUGKIT_USE_USERVER` and `SLUGKIT_GENERATOR_WITH_SERIALIZATION` compile
  definitions **PUBLIC** (required — `SLUGKIT_USE_USERVER` drives pimpl sizes in
  public headers, so every consumer must see the same value), and link
  `userver::core` (now guarded by the option).
- `utf8proc::utf8proc` is linked PUBLIC to `slugkit-generator-utils` for BOTH
  builds (with a `find_package(utf8proc CONFIG)` + imported-target fallback),
  since `text.cpp` now depends on it.
- ⚠ Not buildable in this environment (no userver here); the userver build of these
  CMake changes still needs verifying in the Docker/devcontainer toolchain.

## Phase 3 results — C ABI (`slugkit_c`)

A C ABI now wraps the engine and is verified end-to-end on host.

- **Header:** `slugkit/include/slugkit/c/slugkit_c.h` — pure `extern "C"`, opaque
  `slk_generator*`, `slk_status` codes. Surface: `slk_generator_create`(N binary
  buffers) / `_create_one`, `_destroy`, `slk_random_seed`, `slk_capacity`
  (capacity as an arbitrary-precision **decimal string** + max length),
  `slk_generate` (caller buffer, reports required length on overflow),
  `slk_generate_alloc`, `slk_generate_batch` (callback, no per-slug alloc),
  `slk_string_free`, `slk_version`.
- **Impl:** `slugkit/src/slugkit/c/slugkit_c.cpp`. Opaque handle owns a `Generator`;
  incoming dictionary buffers are **copied into a `shared_ptr` keepalive** and handed
  to `binary::DictionarySet::Add(span, keepalive)` — so construction is from a raw
  pointer+len with no `mmap` and no caller-lifetime constraint. All exceptions are
  caught and translated to status + a heap-allocated message; UTF-8 throughout.
- **No runtime context needed.** Unlike the userver build (the `bin-dict` example
  wraps generation in `userver::engine::RunStandalone`), the standalone build runs on
  a plain thread — exactly what FFI callers need.
- **Verified** by a C (not C++) smoke test (`slugkit/host/c_abi_test.c`, proves the
  header is valid C) loading the committed `emoji.bin`: create-from-buffer, random
  seed, `capacity({emoji})` = 1154 / max_len 1, deterministic generate, buffer
  variant matches alloc variant, buffer-too-small reports required length, batch of 5,
  and a malformed pattern returns NULL without crashing. All checks pass.

### What remains
- **Serialisation layer** (`generator/io/`, `structured_loader.hpp`,
  `string_view_serialize.hpp`, `numeric.hpp` I/O) is still userver-only and excluded —
  needs a userver-free YAML/JSON path (or buffer-only dict construction) for mobile.
- **Verify the userver build** of the CMake flag changes in the devcontainer.
- **Cross-toolchains** (NDK / iOS / wasm) and **per-language bindings**
  (Swift XCFramework, Kotlin AAR, Dart ffi plugin) per Phases 4–6 above. The C ABI
  is the substrate they all bind to.
